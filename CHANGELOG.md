# Changelog

All notable changes to this project are documented here.

## [Unreleased]

## [0.1.9] - Answer the new questions of the server when a job resumes, and the spindle and drill settings

- **Before the tool goes down into the work:** when a job that goes on after a stop waits with `pause.plunge`, the app says that the head is over the point and that confirming takes the tool down, in the eight languages. Needs the server that asks it; not tried on a machine.
- **Preparing a drilling job asks for the number format of a file that does not declare it:** the card of the drilling file offers the formats, with nothing chosen at first and the choice kept on the phone, and sends `drill_format` to the server. A refusal for the format is said in the eight languages with what to choose, and the warning of a file read this way says it was read with the chosen format. 2 new tests; checked by tests, not on a phone against a machine.

- **The settings of the server have the new `grbl_spindle_stop_on_pause`** (off: a pause of a GRBL machine also stops the spindle and the coolant), with its label and help from the contract of the server. Not tried on a machine.
- **The second question before the spindle or the laser goes on:** when a job that goes on after a stop waits with `pause.power_on`, the app says that confirming switches the spindle or the laser on again, in the eight languages. It needs a server with that question.
- **Confirm and Resume answer the question on the screen (safety):** they send back its identifier (`pause.question` of the job), and a server that asks something else by then refuses the answer (`409 question_changed`) instead of taking it as the answer to a question nobody has read. The two new refusals have their text in the eight languages and the settings have the new `answer_needs_question` of the server (106 keys). A server of an earlier version is answered as before.

## [0.1.8] - Orders are sent once, buttons rest without a connection and the new stop and resume of the server

- **An order that sets a machine going is sent once (safety):** a double touch on Confirm could answer the next question of the machine (the spindle start after a tool change) before anybody had read it, and a double touch on "go on" made two jobs. Start, confirm, resume and "go on" are not sent again while on their way and for a second after the server takes them.
- **Nothing is started or let go from old data (safety):** while the server does not answer, Start, Confirm, Resume and "go on" are off. The stop stays at hand.
- **An order with no answer is not told as one that did not happen:** it says that it may have arrived and the machine may be moving; a start with no answer no longer says that the job stays ready.
- **A refused G-code program is explained as the server now judges it** (`422 bad_gcode`: a line that cannot be sent or cannot be judged for certain), and the line and the reason are kept also when the refusal comes from Start or "go on".
- **A plan that comes back late is thrown away:** the tools or the lines of a file chosen before could be shown, and used, for the file or the machine chosen since; Start waits for the plan of what is on the page.
- **Safety text corrected: the spindle is started when a G-code job goes on.** The server now starts the spindle the program had on, after the operator confirms the resume. The switch of Prepare is for the coolant only and its name and warning say so, and the wait before the first move of a resumed job and the help say that the machine goes back on its own and starts the spindle.
- **The reason of a resume the server does not do stays on the page:** when "go on" is refused (`422 bad_request` of `resume-from`), the page of the job keeps the reason of the server and says what to do.
- **The settings page has the five settings of the stop and the resume:** the copy of the contract holds 105 keys (`grbl_stop_wait_s`, `resume_safe_z_mm`, `resume_spindle_wait_s`, `resume_plunge_feed_mm_min` and `resume_position_tolerance_um`, with their texts in the eight languages), and the units millimetres and micrometres are written as `mm` and `µm`.
- **The app declares the eight languages and no other:** `CFBundleLocalizations` of `project.yml` still listed 37 languages and variants and `App/Resources` still held their `.lproj` folders, so the system offered languages the app does not speak. Both now hold only English, Spanish, German, French, Italian, Japanese, Chinese and European Portuguese. `tools/check_ios_build.py` fails on a language too many, one missing or one named twice, in the project description, in the `.lproj` folders and in the app that was built.

## [0.1.7] - Live status of 3D printers, warnings of pick-and-place nodes and the new permissions of the server

- **A node of a pick-and-place machine that is asked too slowly says so:** its card shows the warning of the server (`poll_too_slow`): how often the server asks it, after how long without being asked it goes to its safe state, whether that time is the one the node says or the default of its contract, and what to change (`pnp_node_poll_s`). Eight languages. Seen against a simulator only.
- **The copy of the settings contract and of the error codes follows the server:** `pnp_node_poll_s` is 1 by default and its help says why; the text of `forbidden_scope` also says that a request may give more than the token has or outlive it.
- **The 3D printers the server watches, read only:** the home page lists each printer with its health, state, temperatures, progress, time left, layer and alerts, from `GET /printers` (contract `eh3d.printers.status/1`). What the printer did not say is shown as unknown, never as zero; a server with the list switched off (`501 printers_off`) shows nothing; a server that does not answer keeps the last list, marked as old; an answer that is not the contract says so. Nothing can be sent to a printer and its access code is never read or shown. A help topic and the texts in eight languages come with it. Both apps read the same file of simulated and hostile cases; nothing has run against a real printer.
- **The copy of the settings contract of the server has its 100 keys in 17 groups** (the five keys of the list of printers), and the five new refusal codes (`printers_off`, `unknown_printer`, `bad_printer`, `printer_exists`, `printers_full`) are told in eight languages.
- **The check of the shared case files compares the two pull requests of a change that touches both apps:** `tools/check_shared_cases.py` read only the main branch of the other app, so a change of the case files could never be green in both repositories; it now reads the branch named by `EH3D_PARITY_REF` (the branch of the pull request, as the check of the examples already did) and main when the other app has no such branch. A test covers the choice of the branch.
- **A program with Windows line ends is counted by its lines, the address typed with capitals or a line break is read, and a port is plain digits (the same rules as the Android app):** `Prepare.lineCount` counted characters, and Swift reads a carriage return and a line feed as one character, so a program of Windows line ends was one line and the line to go on from after a stop was cut to it; a line break around an address, a sign in a port and a name made of line breaks were not treated as on the Android app; an address of the version 6 lost its brackets in the origin; a tool number beyond 32 bits is skipped as there. The case files of the address, shared with the Android app, grow by 51 cases, and 30 new tests cover them.
- The shared workflow checker (`tools/workflow_hygiene.py`) is the current one of the documentation hub: the filters under a trigger (branches, paths, types) are no longer read as events.

## [0.1.6] - Authorization of a job by the hash of its toolpath, the eight official languages only and a parity check that follows the branch

- **A job of a machine shows the hash of what it will do and where its authorization stands:** each job of the queue of a machine shows the first twelve characters of its `toolpath_sha256` and a badge: *not authorized* (nobody authorized it), *authorized* (the authorized hash is the present one) or *expired* (the authorized hash is not the present one). A job read from an older server, which says no hash, shows neither the code nor the badge.

- **The button *Authorize* asks twice and the start names the hash that was shown:** for an operator and a job that waits whose present hash is not authorized, *Authorize* asks a second time with the short code and then sends `POST /work/jobs/{id}/authorize` with the hash that was on the screen (the scope `jobs:authorize` is checked by the server). The start, also asked twice, sends the same hash, so a job that changed after it was shown is refused instead of started. A start of a job with no hash keeps the empty body.

- **A refusal for a changed hash reads the job again:** `stale_authorization` and `authorization_required` make the app read the queue again, so the job is shown with its present hash and badge, and tell the person to check the code and authorize it again; the sentence of the refusal comes from the table of texts in eight languages.

- **Only the eight official languages remain:** the app keeps English, Spanish, Italian, German, French, European Portuguese, Chinese and Japanese, the languages of the EH3D programs on the computer. The 29 added languages and the two variants (Brazilian Portuguese and Canadian French) are gone from the picker, the tables (7 files of `Sources/Eh3dCore/Resources/i18n`), the checks (`tools/i18n_check.py`, the parity with the Android app), the tests and the README files; a phone set to another language shows English. Both phone apps changed together and still hold the same tables.

- **The check that the two phone apps agree compares a pull request with the branch of the same name of the Android app:** `EH3D_PARITY_REF` (the branch of the pull request in the workflow) names the branch of the other app to read; when it has none, or on main, the other app's main is read as before. A change that touches both apps can now be proved on two pull requests of the same name before either reaches main.

- **Eleven new sentences in the eight languages and 6 more tests:** the badge, the code, the button and its question, the notice that the job was authorized and the one that it was read again; the reading of the hash and of the authorization, the badge for an authorization of another hash, who is offered the button, the short hash, the two refusals that ask for a new look, and the requests against a server that lives in the test (route, hash in the body, empty body without a hash, a refused start sent once).

- **The copy of the settings contract has the new keys and the new group:** the copy of the contract of the server now holds 95 keys in 16 groups: the group `pnp_nodes` with `pnp_nodes_enabled`, `pnp_nodes_max`, `pnp_node_poll_s`, `pnp_node_silence_s` and `pnp_node_timeout_s`, and `work_require_authorization`. All six are set in `server.cfg`, so the page shows them with their texts in eight languages and says where they are set; the hash of the copy follows the new file.

- **The refusals of the nodes of the pick-and-place machines and of the authorization of a job are told in eight languages:** the table of texts holds `pnp_nodes_off`, `unknown_pnp_node`, `bad_pnp_node`, `pnp_node_exists`, `pnp_nodes_full`, `pnp_node_disabled`, `pnp_node_not_ready`, `stale_authorization` and `authorization_required`, and the three codes of binary G-code and of the LAN link to Bambu Lab printers that the table did not have yet. The copy of the catalog of the refusals kept for the tests is again the whole catalog of the server (163 codes), and the tests check that every code has its eight texts or a stated reason.

- **The home page lists the nodes of the pick-and-place machines, read only:** when the server has a machine of the pick-and-place plugin, the app asks `GET /pnp/nodes` and shows each feeder and head node with its kind, address and machine, whether the server counts it as ready (green) or not (red), the health it reports, the last error of its poll, the numbers it said last and a SIMULATOR ONLY badge. A server where the nodes are switched off (`501 pnp_nodes_off`) shows nothing. The token of a node is never read or shown, and the nodes are registered and changed in EH3D-STUDIO. The authorization of a job (its hash, the button that authorizes it and the hash sent with the start) is only in EH3D-STUDIO for now; a start that the server refuses for lack of it is told with its code.

- **8 more tests:** the reading of the nodes (health, readiness, the numbers they said, a node that does not say, answers of every kind made from a fixed seed, the token that is never read), the request against a simulated server and the answer of a server that has the nodes off, the codes told by the table of texts, and the copy of the contract with 95 keys in 16 groups.

## [0.1.5] - The values in force of the settings of the server for any login, with a hash that tells when the list of the app is out of date

- **Anyone who signs in sees the values in force of the settings of the server:** the page of the settings used to show every login but an administrator with the policy scope only the copy kept in the app, with no values. It now asks `GET /settings/values` (the light, read-only view that a viewer, an operator or an administrator whose token cannot read the contract may read) and draws the labels, help and warnings of the copy with the value in force of each key, read-only. An administrator who can read the full contract still gets the full page. A key marked secret shows no value, a key the server keeps back (a path of its computer) says that the server does not show it, a long value that the server cut ends with "…", and a key that neither the contract nor the copy lists is drawn as a read-only line.

- **The answer is kept and asked again with its ETag:** the tag of the last answer is sent back in `If-None-Match`, a `304` keeps the page as it is, and the tag is forgotten when the login changes or a read fails. Only a tag of printable characters, at most 96 of them, is kept or sent back.

- **An answer that cannot be trusted is not drawn half:** an answer that is cut, longer than 16 KiB (also when the server does not say how long it is), of another schema (a newer one is told apart), nested deeper than 16 levels, with a key that is not a name of lower-case letters, digits and underscores, an entry that is not an object, a value that is an object, a text longer than 1024 characters, a list of more than 64 items, more than 256 keys or a `count` that is not the number of keys is refused whole, and the page shows the copy with the reason. A value of `***` or `secret: true` is never kept, whatever the server sent in its place.

- **The page says when the list of the server is not the copy of the app:** `tools/sync_settings_contract.py` also writes the SHA-256 of the copy (line ends as LF) into `ContractHash.swift` and checks it, with or without the server next to this repository; the app compares it with the `contract_hash` of the answer and shows a notice in the eight languages when they differ.

- **Four new sentences in the eight languages:** the one that says the values come from the light view, the one for a list that is not the copy, the one for a key the server does not show, and the one for the copy shown when the values cannot be read. The table of the page now has 35 sentences.

- **The copy of the settings contract is the newest file of the server:** it now describes the light view in `read_light`; no key was added, changed or moved.

- **48 more tests:** a good answer, secrets, keys kept back, cut values and keys changed through the security page, the answers refused whole (cut at every length, too long, wrong schema, hostile keys, entries, values, counts and depth), the hash of the copy against the one of the server and against the file, the limits against the contract, the tag that is kept and the one that is not, the choice between the full contract and the light view by role, the `304`, an old server without the route, a refused login, an answer over the limit with and without a length, and the client against a simulated server.

It runs in the CI, and `tools/check_app_parity.py` now also fails when the two phone apps carry a different copy or a different table.

## [0.1.2] - Login that renews itself, sessions, retries, connection settings and every refusal code in eight languages

- **The login is renewed by itself:** the answer of the login now gives the id of the login and how long it lasts (`expires_s`); a request that finds the login in the last quarter of its life first renews it with `POST /auth/refresh` (once, and only for a person's login), a session kept from the last start is renewed when the app opens, and a refusal with 401 makes the client forget the token while a 403 keeps it. Signing out now uses `POST /auth/logout`.

- **The open logins are listed and can be closed:** More shows the logins of the person with their application and address (this phone is marked), closes one with `DELETE /auth/sessions/{id}`, and has a button that ends the login on every device (`POST /auth/logout-all`).

- **Every refusal of the server has a text in eight languages:** `Sources/Eh3dCore/Resources/server-errors.json` holds the 143 codes of the catalog of the server in English, Spanish, Italian, German, French, European Portuguese, Chinese and Japanese. `tools/gen_server_errors.py` writes it from the catalog of the server and the `err_<code>` rows of Studio, so both say the same words; the 28 codes that Studio does not have yet (the laser, the pick-and-place machine, the 3D printer, the jog and the Gerber files) are in `tools/server_errors_extra.json`. The other 29 languages show the English text of a code that only this table has. A test fails when the table is not the catalog of the server (it is skipped when the server folder is not next to this one).

- **Time-out, retries and an optional search on the network are settings of the connection:** More has the time-out of each try (1 to 120 s, 15 by default), the retries after a failure on the network (0 to 5, 2 by default) and a switch for the search of the server on the local network, off by default. After a failure the client waits 200 ms, 400 ms, 800 ms... up to 2 s; a connection that could not be made is tried again for any request, a time-out or a 502, 503 or 504 only for the requests that do no harm twice, and a POST (a job, a login) is never sent twice.

- **The search for the server on the local network is optional:** with the switch on, the sign-in can look for `_eh3d._tcp` with Bonjour (`NWBrowser`) for 8 seconds and lists up to 8 IPv4 servers that answer; the person picks one, nothing connects by itself and the password is still asked for. The service is declared in `NSBonjourServices` and the system asks for the permission of the local network the first time. It has not run on an iPhone.

- **The machines of the plugins are shown with their detail:** the home page lists the machines of the other plugins of the server (`GET /work/machines`, such as the laser, the pick-and-place machine and the printer) under the drilling and routing ones, with what each says of itself in `detail` and a red mark when it is latched by an emergency stop or an alarm.

- **63 more tests:** the client is tested against a stand-in server that renews and lists logins, ends them, is busy for a moment and fails a number of times, and the tests follow the renewal in the last quarter, the forgetting of a refused token, the retries and their pauses, the POST that is not sent twice and the connection that could not be made; the rules of the connection, the sessions, the machines of the plugins, the candidates found on the network and the table of refusals have tests of their own.

- **The texts of the new settings are in the 37 languages:** 12 phrases (the settings of the connection, the open logins and the other machines) in every table, the same as in the Android app.

- **The login goes through the single login of the server:** the app signs in with `POST /auth/login` and says it is the `ios` application, so the server keeps the application with the login and in its audit (it used the first, application-less route before).

## [0.1.1] - Newest improvements of the iPhone and iPad app

- **A stop that the ended session refused is sent again after signing in:** the machine ids are kept in memory only, for two minutes, so signing in late never stops a job that was started afterwards; the person is told at once that the stop did not arrive.

- **The warning that a drill file did not state its unit is written in the language of the app:** the server's `units_supposed` warning had no phrase of its own and showed as a generic server warning; it now has its text in the 37 languages.

- **A reinstalled app no longer opens with the session of the earlier install:** the Keychain survives an uninstall and the preferences do not, so the first start of an app with no saved setting forgets the kept session (an updated app keeps it). A unit test covers both cases.

- **A stop that is refused because the session is no longer valid says so, and "stop all" reaches every machine:** the plain notice that the stop did NOT arrive is shown before the app returns to the sign-in, and the stop of the whole fleet is sent to every machine the fleet lists, not only to those with a job in the last reading. Same as the Android app. A stop that got no answer at all is sent once more after 250 ms before the notice is shown; an answer of the server is final.

- **A saved certificate pin now needs a real chain:** when the system does not trust the chain, the pin counts only if the chain is evaluated again with the pinned certificate as the only anchor (signed path from the leaf, in date, made for the host). Before, a chain that merely held the pinned certificate behind a forged leaf was accepted. Servers already paired keep working. Tests cover the decision with and without the proof.

- **A reply that is not JSON is the wrong server, not a lost connection:** `classifyFailure` now checks the `bad_json` code before the status, so a body that is not the JSON of EH3D-SERVER is told as another service on the address even when the client could read no status from it (the old order called it no connection). The test that fixed the old behaviour is changed, the case is added to the case files shared with the iPhone app and to the scenarios of the simulated server.

- **Simulation of the stops and of the notices, ported from the Android app:** add `Tests/Eh3dCoreTests/StopScenarioTests.swift`, a simulated EH3D-SERVER with a memory (one machine, one job; a stop reaches the machine two looks later; the server can be made unreachable) and a phone that looks at the fleet every second and a half with the real client and the real rules of the stops and the notices. Three tests cover a stop that is sent, then still working past the grace, then confirmed and gone after a while; a machine that does not stop; and an outage that makes no notice while the changes that happened meanwhile are told when the server is back. Nothing has run against a real server or a phone.

- **A simulated server that goes away and comes back:** `OutageScenarioTests` drives the real client and the real rules of the link against a stand-in that is unreachable, answers 503, answers as another service (a 404 page) or refuses an old session, with a seeded run of 30 outages. It checks the state shown (connected, stale, no connection, wrong server), the longer waits between retries and the return to connected with the first good answer. Not run against a real server on a phone.

- **A floor of coverage in the CI:** the build stops when the tests cover less than 89 % of the lines of the package of rules (it is 91 % today, it was 72 % before the last tests); the screens of the app are built with Xcode and are not counted.

- **112 more tests, a check that the two phone apps agree and a measure of coverage:** the client of the API is tested against a server that lives in the test (paths, methods, headers, bodies, refusals, a service that is not JSON, a server that is away), the pins of the certificates, the cutting of the live camera into pictures, the wait before asking for it again and the readers of the answers of the server are tested from their edges, `tools/check_app_parity.py` fails when the examples of the answers, the catalog of the refusals or the tables of the 37 languages differ from the ones of the Android app, and the CI prints how much of the package of rules the tests cover (`tools/check_coverage_floor.py`).
